# Vehicle controls: official SDK review

Reviewed on 2026-11-15 (Asia/Seoul), including the current official contest clarification. This document supports the vehicle-environment web simulation and a later native SDK handoff. The current web screen does not query or control a physical vehicle. Project adapter names are application interfaces, not official Pleos classes or methods.

## Availability and current scope

Contest [notice 08](https://appdevchallenge.auto-hmg.io/notice/c0a1a000-2026-4923-8000-000000000008) permits emulator development/testing of documented **Vehicle, NaviHelper, TextToSpeech, SpeechToText and FusedLocation SDKs** despite a preparing workspace status. The [portal guide's](https://document.pleos.ai/docs/pleos-only/create-my-project) status is **not an emulator-development ban**. Notice 08 also permits Gleo App Schema without separate approval; unpublished SDKs and Pleos LLM SDK are not supplied.

This establishes the contest's permitted development scope, not a completed integration in STARLIGHT PLEOS. The React/TypeScript vehicle adapter remains browser-local demo code. A separate Android package or successful Android build does not, by itself, establish Pleos SDK initialization, a Pleos Connect emulator connection, actual property observations or physical control. **Pleos Connect emulator SDK behavior and real-car behavior have not been verified in this SDK review.** The native handoff still needs API permissions, capability/area/range checks, observed values, error handling and platform driving restrictions.

The [Vehicle setup guide](https://document.pleos.ai/en/docs/pleos-only/connect-sdk-pleos/Vehicle/project-setup) showed the Android Gradle dependency `ai.pleos.playground:Vehicle:2.3.2` when reviewed. This is a reference example, not a claim that the web app declares that dependency or that an accompanying Android package has connected it. Native development must use and record the actual compatible SDK/emulator versions. The app's browser speech playback is not Pleos TTS/STT SDK integration.

## Native request and confirmation flow

1. Initialize the SDK and obtain the appropriate domain object; release listeners/resources at the correct lifecycle point. The official [domain-object guide](https://document.pleos.ai/en/docs/pleos-only/connect-sdk-pleos/Vehicle/obtain-domain-object) describes asynchronous IPC rather than synchronous return values.
2. Declare permissions required by each API's `@RequiresPermission`. [Permission documentation](https://document.pleos.ai/en/docs/pleos-only/connect-sdk-pleos/Vehicle/vehicle-permission) distinguishes read `CAR_*` from control `CONTROL_CAR_*`. Read access does not authorize control; verify actual constants instead of inventing permission names.
3. Check [capability](https://document.pleos.ai/en/docs/pleos-only/connect-sdk-pleos/Vehicle/check-capability) before enabling an action. The documented shared model distinguishes `NONE`, `READ`, `WRITE`, `READ_WRITE`, supported areas and bounds. Return types can differ by API. Use the target vehicle's data, not the simulation's default temperatures, window percentages or seat positions.
4. Read the current value and subscribe to updates. [Get](https://document.pleos.ai/en/docs/pleos-only/connect-sdk-pleos/Vehicle/get-property) uses `onComplete(value)` / `onFailed`; [Callback](https://document.pleos.ai/en/docs/pleos-only/connect-sdk-pleos/Vehicle/callback) uses registered listeners with `onXxxUpdated` / `onFailed`.
5. Submit a control request and show a pending state. The general [Set guide](https://document.pleos.ai/en/docs/pleos-only/connect-sdk-pleos/Vehicle/set-property) documents failure through `onFailed`; the API-type table does **not** promise a Set success callback. A sent request or absence of an immediate error is not verified physical completion. Confirm the observed value through a listener or a subsequent read before labeling it applied. Track request order and discard obsolete callbacks in the application adapter.
6. Map [documented errors](https://document.pleos.ai/en/docs/pleos-only/connect-sdk-pleos/Vehicle/vehicle-error-code) to useful UI: unsupported property/area, permission denied, connection failure and driving restriction. `onFailed` receives an `Exception`; inspect `VehicleException.errorCode` only when that subtype is present. Handle timeouts and stale observations as application states and never display an old value as a newly confirmed result.

The native app must also subscribe to the platform's [driving restrictions](https://document.pleos.ai/docs/pleos-only/vehicle-app-developer-guide/driving-restriction-development-guide). A speed of zero does not establish parking or permission for an immersive mode. Simulator test switches remain in the developer panel.

## Planning trace and truthful UI states

The supplied 2026-11-13 planning PDF page 7 conditions HVAC, light, window and seat controls on SDK availability, rights, vehicle/area support and observed behavior. Read that availability condition with notice 08's emulator allowance above; capability and observed behavior still need testing. Presentation PDF pages 29–32 (screen IDs 23–26) provide the vehicle-care, window, HVAC and light/sound/timer concepts. The current web screen demonstrates selection, requests, cancellation and simulated readback; it must label the source as simulation. Unsupported, denied, disconnected, stale and request-failure states need distinct presentation.

Battery/range/lock and cabin sensor readings are observations, not commands. Simulated values must remain labeled; unavailable CO₂/CO sensors stay unavailable. Manually selected condition is self-report, not health diagnosis. The app timer stops app content; vehicle power, HVAC shutdown, automatic driving/SOS, sunroof actuation and roof projection are not implied. Presentation page 32 and planning page 12 explicitly separate those future/unsupported effects from the app timer.

This is a source review and UI/adapter handoff document. It establishes no permission grant, native compilation, emulator connection, real-car control, physical safety certification or display/projection hardware support.
